# Weeks 2–3 Learning Specification

This is the content specification for the existing Learn → Apply → Check → Evidence engine. It is intentionally separated from the application shell so the curriculum can be expanded without destabilising the production UI.

## Week 2 — MicroStation CONNECT Fundamentals & Level Structures

### Learn
- Understand the difference between design intent, model organisation and sheet presentation in MicroStation CONNECT.
- Use levels as a controlled drawing-management system rather than as personal drafting shortcuts.
- Establish a predictable seed/template workflow, working units, references, level naming and annotation conventions before production work begins.
- Understand how references, models and sheet composition affect coordination and downstream review.

**Senior takeaway:** A senior designer should be able to explain the structure of a MicroStation file/package and make it understandable to another designer without reverse-engineering the setup.

### Apply
Scenario: A fictional switchroom package is being migrated into a controlled MicroStation CONNECT environment.

Tasks:
1. Define a level structure for equipment, power, cable containment, text, dimensions, references and construction aids.
2. Define five pre-drafting checks covering seed file, units, references, levels and annotation/plotting requirements.
3. Identify three likely coordination risks caused by poor reference or level management.
4. Produce a sanitized setup sheet or annotated screenshot demonstrating the proposed structure.

Deliverable: A reviewable MicroStation setup plan with assumptions and verification notes.

### Check
1. What is the strongest reason for standardising levels across a package? **Answer:** Consistency, reviewability and controlled downstream editing.
2. What should be confirmed before importing or attaching reference information? **Answer:** Coordinate/model context, source revision, units/scale and project requirements.
3. A designer says, “My levels work, so the package standard is unnecessary.” **Best response:** Package standards reduce ambiguity and rework and allow another designer/checker to work safely.

### Evidence
Capture a sanitized level/reference setup artefact and explain:
- the design intent;
- the conventions selected;
- assumptions/interfaces;
- how another designer would verify the setup.

## Week 3 — Electrical Documentation Standards & Drawing Ownership

### Learn
- Treat electrical drawings as controlled engineering deliverables, not isolated drafting outputs.
- Understand revision status, redlines, design intent, references, notes, legends and cross-discipline interfaces.
- Distinguish drafting changes from design decisions and identify when a decision needs design-lead/client approval.
- Use a repeatable self-check before issue: content, references, consistency, constructability, revision and presentation.

**Senior takeaway:** Drawing ownership means understanding what the sheet communicates, what inputs it depends on, what changed, who needs to review it and what must be verified before issue.

### Apply
Scenario: A fictional cable-block drawing receives redlines affecting cable identifiers, containment references, notes and revision information.

Tasks:
1. Classify each markup as drafting correction, coordination item, design decision or approval-dependent change.
2. Create a disposition list showing action, owner, required input and verification method.
3. Update a sanitized drawing/revision record.
4. Perform a final issue-readiness check and identify unresolved items.

Deliverable: A redline disposition/QA record plus a sanitized before/after example.

### Check
1. A redline conflicts with the latest approved design information. **Best response:** Do not blindly implement it; flag the conflict, confirm the controlling input and obtain the required decision.
2. Which statement best demonstrates drawing ownership? **Best response:** The designer can explain the drawing's purpose, inputs, interfaces, changes and verification status.
3. Why should unresolved assumptions be visible before issue? **Best response:** They can affect design intent, coordination, constructability and approval risk.
4. A sheet looks correct but its referenced detail is an obsolete revision. **Best response:** Treat the reference as an issue to resolve before release, not as a cosmetic problem.

### Evidence
Capture a sanitized redline-disposition/QA artefact showing:
- markup interpretation;
- decision/approval boundary;
- revision/reference control;
- final verification.

## Integration contract

Each week must appear in the existing module list and use the existing four-stage modal flow. Completing a stage should persist state, update the 96-activity program count, contribute to Home's next-best-action logic, and expose completed evidence in Portfolio. Evidence should remain linked to the related week. Journal remains the reflection mechanism and should not be duplicated inside the course engine.

The content should be rendered as structured cards, not a long undifferentiated text block. Knowledge checks must save answers and score. Evidence must require a title and description before completion. All content must support sanitized/fictional work samples and must not encourage disclosure of confidential employer/project information.
